# Roadmap: the future topics of the software factory

This file is the one list of what the factory may build next. Sebastian uses it to set priorities. Every item here is open: not built, not scheduled, or built only in part.

Sebastian decides what gets in and what goes out. An item enters when he accepts it, defers it or names it as a candidate. When an item is built, its record moves to the stage paragraphs of the [build plan](plans/2026-09-24-build-plan.md) and the item leaves this file. A rejected item stays in the last section with its reason, so it is not proposed again by accident.

## The guiding principle: primitives, not a process

The factory ships no fixed development process. It ships small primitives, and a user composes them into the process they want. Each primitive is a plain YAML block with a schema, in the spirit of Kubernetes objects but without Kubernetes vocabulary (ruling 184). `factoryd config check` refuses a composition that cannot work: a cycle, a lane that starts tasks with no class that may code, a queue on a stage that does not exist. Every item below is built as such a primitive.

## How to read an item

Each item names its sources, its status, a size where a source gives one, and a `Priority` field that Sebastian fills in.

- **Status.** Decided: Sebastian wants it, not yet scheduled. Candidate: named in a source, not ruled. Deferred: revisit later, usually on a named trigger. Accepted risk: a known weakness kept on purpose. Rejected: not wanted, with the reason.
- **Sources.** Plan: the [build plan](plans/2026-09-24-build-plan.md). Its lists of 2026-09-29 (the harness list, the market list, the second and third rounds) now live here, cited with their old numbers, which git history keeps. Arch: [architecture.md](architecture.md). Target: [target-architecture.md](target-architecture.md). Synthesis: [market research synthesis](market-research/SYNTHESIS.md). Goal: [goal.md](goal.md). Queue, backlog and handover: the ledger files [stage10-queue.md](../.superpowers/sdd/2026-09-24-build-plan/stage10-queue.md), [stage9-backlog.md](../.superpowers/sdd/2026-09-24-build-plan/stage9-backlog.md) and [handover-stage11.md](../.superpowers/sdd/2026-09-24-build-plan/handover-stage11.md), which are local to the controller's machine. 2026-09-30: Sebastian's discussion with the controller on that day.

## Next

**1. Build software from a spec on an empty board.** The factory so far fixes and improves existing code. This stage makes it build a new application from a written spec, with several agents in parallel. The parts:

- A new project from the console: a button opens a pull request on the infra repository that adds the project file (ruling 183 stays), with a loading indicator, status updates and tooltips while it runs.
- Two new board columns. Backlog holds cards that do not start. A card in Ready starts. The `agent` label stays the mechanism underneath.
- A plan card: a planner session proposes a plan with subtasks, and the human comments until they accept it. On acceptance factoryd, not the model, creates one child card per subtask in Backlog, linked to the plan and to its dependencies.
- A "Start plan" button moves all child cards to Ready. A card whose dependencies are not done waits in Ready ("waiting on #n") and starts by itself when they are done.
- The foundation card comes first and every other card depends on it: layout, CI, API contract, schema and one end-to-end test. A final integration card runs the spec's acceptance tests.
- A merge queue, one per project in the first version.
- The app: a new project from an empty repository, a link shortener with a TypeScript single-page frontend and a Go API. About ten cards: foundation, link API, redirects with click counting, accounts, three or four frontend pages, rate limiting, QR codes, deploy and integration. A public stats dashboard and an admin area are optional.
- Needs: Node and npm in the worker image and in CI, and a checks stage that works on an empty repository.
- Exit test in outline: a spec card on an empty board becomes a deployed app, with at least four agents working in parallel.

Sources: 2026-09-30 item 2. Goal ("agents create software from specs"). Queue J44 and plan second round 9 (blocker-aware dispatch, which the waiting cards cover). Queue H26 patterns 6, 9 and 10 (an editable plan gate, card links, agents filing their own sub-cards). Synthesis sections 6 and 8 (plan approval before code, Large). Status: decided in outline, details to rule. Size: one stage. Priority:
