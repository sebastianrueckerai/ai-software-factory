# Roadmap: the future topics of the software factory

This file is the factory's memory for future work. Its purpose is that nothing gets forgotten: every idea, wish, deferred item and known weakness that is not built lives here, in one place, where Sebastian can set priorities.

It is not a record of rulings. Items get fuzzier the further out they are. Many will change, conflict with the plan or go stale, and deleting a stale item later is fine. A remark in a discussion is not a final decision. Where a ledger ruling does decide something, the item cites it. When an item is built, its record goes to the stage paragraphs of the [build plan](plans/2026-09-24-build-plan.md) and the item leaves this file.

## Three guiding ideas

**Primitives, not a process.** The factory ships no fixed development process. It ships small primitives, and a user composes them into the process they want. Each primitive is a plain YAML block with a schema, in the spirit of Kubernetes objects but without Kubernetes vocabulary (ruling 184). `factoryd config check` refuses a composition that cannot work: a cycle, a lane that starts tasks with no class that may code, a queue on a stage that does not exist. Every item below is meant to be built as such a primitive.

**Fewer manual steps than the competition, with enough security.** The goal is software built and improved without human input. The factory aims for fewer manual steps and gates than other products while keeping the security it needs. Today the factory's own repositories stay on the `human` merge rule, and every `auto` merge rests on the review's approve. Items such as the answer chain, blocked with a next action, mutation testing and the intervention rate give the evidence for taking the next step. Source: [goal.md](goal.md).

**Limited scope, full context, simple prompts.** Each step an AI takes has a limited scope. It gets all the context it needs, including the history of the steps before it, all the tools it needs, tools to gather more, and a clear view of the goal. It checks its own work and corrects itself. Then its prompt stays simple, with no special-case rules. A prompt rule stays possible where nothing else carries it, but it is brittle, and such rules accumulate. A weak spot gets its fix in code, in a tool's shape, in a check or in the configuration, not in a sentence of a prompt. Stage 16's four principles ([architecture.md](architecture.md) 5.7) are this idea's first form: no rule in a prompt that a tool or a deterministic step can carry, every console read is a tool, self-correction over prevention, and a small default context with depth fetched by tools. This idea adds the scope: a step that is too large is made smaller by construction, not by asking. Every finding below names its fix in this way. Source: Sebastian, 2026-10-12.

- **108. A dedicated server for microVMs.** Sebastian refused bare-metal nodes. Sources: queue J. Where it stands: rejected, not to be proposed again without his asking.
- **109. A reader and writer split.** Every agent keeps the exact input, and the optional injection scan (item 45) guards it instead. Sources: arch 10, synthesis section 5. Where it stands: rejected (Sebastian, 2026-09-29).
- **110. Command-level policy in the sandbox.** Allowlisting every legitimate command is an endless race, so the sandbox allows everything and the blast radius stays contained. Sources: arch 10, synthesis section 5. Where it stands: rejected (Sebastian, 2026-09-29).
- **111. Typed side-effect requests applied after the agent.** A deferred list could refuse one of several actions that only make sense together, so the side-effect tools are live (item 29). Sources: queue J39, synthesis section 5. Where it stands: rejected.
- **113. VS Code Remote Tunnels and SSH into the pod for "I am going in".** Tunnels need egress to Microsoft's relay and a Microsoft or GitHub identity. Sources: queue H25. Where it stands: ruled out in the queue.
- **114. Harvester.** Its current release warns against upgrading, and its floor of 16 cores and 64 GB per node does not fit cheap boxes. Sources: arch 9, goal. Where it stands: dropped.
- **157. A second factoryd replica to keep sessions across a roll.** Stage 15 found that every roll, a restart of factoryd's one replica, stopped the running sessions. Ruling 269 chose the roll's session gap instead, built in Stage 16: a roll merges only when no session runs, and new sessions wait while it does. A second replica was rejected, since the runner's live sessions, the timeline lock, the event bus and twelve loops assume one process: two replicas would double every pulse call, and the gate supervisor assumes one too (item 91). A pod drain was rejected as well, since the Service drops a terminating pod, so the console and webhooks would be down for the drain. Sources: Stage 15 (00:33Z, 05:49Z), Stage 16 (11:4xZ). Where it stands: rejected by ruling 269.
