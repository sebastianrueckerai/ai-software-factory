# Roadmap: the future topics of the software factory

This file is the factory's memory for future work. Its purpose is that nothing gets forgotten: every idea, wish, deferred item and known weakness that is not built lives here, in one place, where Sebastian can set priorities.

It is not a record of rulings. Items get fuzzier the further out they are. Many will change, conflict with the plan or go stale, and deleting a stale item later is fine. A remark in a discussion is not a final decision. Where a ledger ruling does decide something, the item cites it. When an item is built, its record goes to the stage paragraphs of the [build plan](plans/2026-09-24-build-plan.md) and the item leaves this file.

## Two guiding ideas

**Primitives, not a process.** The factory ships no fixed development process. It ships small primitives, and a user composes them into the process they want. Each primitive is a plain YAML block with a schema, in the spirit of Kubernetes objects but without Kubernetes vocabulary (ruling 184). `factoryd config check` refuses a composition that cannot work: a cycle, a lane that starts tasks with no class that may code, a queue on a stage that does not exist. Every item below is meant to be built as such a primitive.

**Fewer manual steps than the competition, with enough security.** The goal is software built and improved without human input. The factory aims for fewer manual steps and gates than other products while keeping the security it needs. Today the factory's own repositories stay on the `human` merge rule, and every `auto` merge rests on the review's approve. Items such as the answer chain, blocked with a next action, mutation testing and the intervention rate give the evidence for taking the next step. Source: [goal.md](goal.md).

## The project screen, members and notifications

- **145. The notification service.** The factory emits events (a human is needed, a task failed, a task or project completed, a budget warning, a project paused), and a notification service decides whether one notifies, reads the member's preferences and sends it to a channel. Project logic never names a channel. Channels in order: Web Push from the installed PWA first, Telegram second, Discord third, WhatsApp last. What notifies: you are needed, something important failed, the budget needs attention, a project or milestone is done. Routine agent activity never notifies, since the pulse covers it: the pulse is awareness inside the factory, a push is something worth pulling a person back in. A tap opens the mobile browser on the card that waits, the member answers and closes the phone. The conversation's facts: Web Push needs no app store and no developer programme, on iOS 16.4 and later for home-screen web apps (the permission asked after an explicit user action) and on Android through Chrome and Firefox, with a service worker, the Push API and VAPID keys on the server. The Telegram and Discord bot APIs are free and a bot needs no phone number. A Telegram user starts the chat once, since a bot may not open one, and Telegram's inline buttons can carry a choice straight back into the event stream. WhatsApp's Cloud API needs a Meta business setup and a verified sending number in production (a test number reaches five recipients in development), and since 1 July 2025 a business-initiated message outside the 24-hour window needs an approved template and may cost a fee per message. Signal has no official bot platform, and `signal-cli` is unofficial. The board roadmap's "Approvals on the phone" (old 29, a push channel plus a small approval page, with [Nimbalyst](board/reports/nimbalyst.md)'s iOS path and Happy's push approvals as the field's proof) and architecture 10's "Approval on the phone" fold in here. Sources: UX conversation, ruling 256, the board roadmap. Where it stands: wanted by Sebastian, after Stage 15 (ruling 256). Priority:
