# A chat door for a human's own agent: implementation plan

Written 2026-11-02. Status: built and live on 2026-11-02. Code main
fdf4d793 to 44c60082 (19 commits), then 1b7c5367 (C43 in the comments),
03b204bd (a racy chat test) and 8ff57da9 (the 50-second wait). It went
live with the roll of 321baaa at 19:38 UTC. It answered fault 7 of
[docs/needed-fixes.md](../needed-fixes.md), which has left the register.

The live proof ran as `controller`, an approver, from 19:38 to 21:50 UTC:

- Two tokens came from the form on `/notifications`. The answer was
  `no-store`, it showed the bearer once, and the page never showed it
  again. The table holds only the hashes and the sealed Forgejo tokens.
- `chat_threads` answered. A `chat_send` turn read the board with its tool
  and quoted it in 11 seconds. The token's thread did not become the
  human's current one, and the browser still showed it unread after
  `chat_read`. Every row named the token.
- On the infra project, a confirmed edit of card #1 and its revert went
  through `chat_confirm`. Forgejo recorded the edit under `controller`, the
  event `card_edited` carried the token, and a second press of the same
  proposal was refused.
- A turn of 25 tool calls took 86 seconds through the edge and came back
  whole.
- Claude Code 2.1.309 cuts an MCP tool call at 60 seconds by default, so
  `chat_send` waits 50 seconds. A stock client then got `ended: false`
  after 58 seconds, and `chat_read` read the rest.
- Forgejo 17.0.1 answered the token probes as designed: 403 for the admin
  and notification reads, 422 for `[]` on issues and pulls, and 403
  naming the scope for a token that lacks it.
- A revoked token got 401 on its next call.
- The door then carried real work: it answered #1441 and #1474, steered a
  session, closed #1441 into a successor and funded the chat from €30 to
  €50 with `chat_fund`.

The build departs from the text below in four points. A fifth tool,
`chat_fund`, funds a spent chat. `chat_read` answers `{"messages",
"more"}`, paged by size as well as count. The made and revoked events
carry the stamp's shape. `chat_send` waits 50 seconds, not 4 minutes.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A human makes a chat token for one project in the console, adds it to Claude Code as an MCP server, and Claude Code sends turns, reads threads and presses Do it in that project's chat as that human, with every row it causes naming the token.

**Architecture:** A `chat_tokens` table holds the SHA-256 of each bearer and the human's own Forgejo token, sealed. The console serves `POST /mcp` with the MCP Go SDK behind a bearer check of its own. The check builds a session with the human's login and the sealed Forgejo token, so every existing access check and Forgejo call works unchanged. `chatPost` and `chatProposal` are cut so the browser and the four MCP tools run one turn path. The token's name goes into events and chat rows at the two store seams every write passes.

**Tech Stack:** Go 1.25, Postgres migrations, `github.com/modelcontextprotocol/go-sdk` v1.8.0 (already in `go.mod`), Go templates, the console's test rigs and fakes.

**Spec:** [docs/chat-door-design-2026-11-02.md](../chat-door-design-2026-11-02.md). Read it first. It holds Sebastian's four decisions, the reasons for the sealed Forgejo token and the threat surface.

## Global Constraints

- `go test -race ./...` green, `gofmt -l` empty, `go vet ./...` and `gosec` clean before every commit.
- The bearer is `sfc_` followed by 32 random bytes in base64url without padding (43 characters). Only its SHA-256 hex is stored.
- Lifetimes are 7, 30 or 90 days, 30 by default. No token without an expiry.
- The Forgejo token is the human's own, with the scopes `read:user`, `write:repository` and `write:issue`. It is sealed with `sealed.Seal(SessionKey, "console-chat-tokens-v1", tok, hash)`, the token's hash as additional data.
- `/mcp` reads only `Authorization: Bearer`. It ignores cookies. Every other route ignores a bearer. Unknown, expired and revoked tokens get one 401 text: `unknown, expired or revoked chat token`.
- The tools are exactly `chat_send`, `chat_read`, `chat_confirm`, `chat_threads` and `chat_fund`. The final review added `chat_fund`. `chat_send` waits at most 50 seconds, inside Claude Code's default 60-second tool timeout, which the live proof measured.
- Nothing on a token's path calls `MarkSeen`, `OpenConversation` or `NewConversation`, or reads an `owner`.
- No chat tool reads, makes or revokes a chat token.
- Copy says human, never member, operator or resource.
- Comments only for what code cannot say. Tests derive their expected values by hand.
- Each task is one commit on the worktree branch, one line in the repository's voice. No ledger paths or ruling numbers in tracked files or commit messages.
- Line numbers are code main 5c2bb4b4. Grep again before editing.

## Review Focus

1. Two Claude Code sessions on one token send their first turn at the same moment. Both land in one side thread, not two (Task 1's `ClaimChatTokenConversation`, Task 4's test).
2. The human revokes a token while `chat_send` waits. The running turn finishes, and the next call gets 401 (Task 4).
3. A token's project leaves the policy tree or is renamed. The call is refused with `project <repository> is gone; make a new chat token` (Task 3).
4. A bearer pasted with spaces or a trailing newline works. A bearer under the scheme `token` instead of `Bearer` gets 401 (Task 3).
5. The chat's budget stops a token's turn. `chat_send` answers with the budget stop and `ended: true`, not a timeout (Task 4).
