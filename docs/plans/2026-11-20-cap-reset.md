# A human resets a cap's count: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a human restarts the count of the day cap, the factory's month cap or a project's month cap from the console's status panel at any time, the cap in the policy stays, and no agent can do it. The strip always shows the day and the month, and any other limit only once it is hit.

**Architecture:** a `cap_resets` table in the gateway's database. The SQL expressions that count spend against a cap (`internal/policy/holds.go`) count the ledger rows booked since the newest reset in the cap's UTC period, so the gateway, factoryd and the console enforce and show the same count. A console form, behind a human's cookie session and CSRF, writes the reset and wakes the cards that wait on a cap. factoryd reads LiteLLM's proxy budget, the absolute monthly limit, for the panel.

**Tech Stack:** Go, PostgreSQL, html/template with htmx, Temporal (the existing cap waits), LiteLLM's admin API.

**Spec:** C47 in `design/design-decisions.md` of `~/repos/ai-software-factory`, and this file. The round: `design/rounds/20-cap-reset/` (reference `reference.png`; where it differs, C47 holds). Code in `~/repos/ai-software-factory-code`, from `origin/main` 94e5a9f21 or later.

## Global Constraints

- The caps reset: `day` (`budget.day_eur`), `month` (`budget.month_eur`), `project` (`budget.month_eur` in `projects/<name>.yaml`). The premium cap, the judgment budget and the escalation pool have no reset.
- A reset never changes the policy. It moves the start of a cap's count inside the cap's current UTC period; a reset of an earlier period has no effect.
- Human only: a form route with a cookie session and CSRF. No chat tool, no MCP tool, no ladder rung, no factoryd code path writes a reset.
- Who: `day` and `month` need a factory writer (`factoryWriter`, scope `scFactory`); `project` needs an approver of that project (`approver`, scope `scProject`).
- Hit: a cap is hit when its count reaches the cap or the gateway refused a call at it since its count started (`policy.CapHit`).
- Copy is lower case on the strip and in the panel notes, sentence case in the confirm, as written below. Money as `textutil.EUR` (two decimals) with " EUR"; the backstop in USD.
- Comments only for what code cannot say, in the file's voice. No ruling numbers and no ledger paths in code, tests or commit messages (`.githooks/pre-commit`).
- Tests: hand-derived expectations, never tuned to pass. `go test -race` on every package a task touches; `gofmt -l` empty; `go vet` clean.

## Review Focus

1. A card waiting on a cap after a reset: `CapResume` today skips its funding check when the refusal came after the policy version in force settled, and a reset changes no version. Without Task 2's change, no card resumes before the period turns (Task 2, `TestCapResumeAfterReset`).
2. A reset while holds are outstanding: the count after the reset still includes every outstanding hold, so the reset gives one cap's worth, not more (Task 1, `TestResetKeepsHolds`).
3. A reset of an earlier period: yesterday's day reset and last month's month reset leave today's and this month's counts whole (Task 1, `TestResetOfAnEarlierPeriod`).
4. Two resets in one period: the newest sets the start (Task 1, `TestNewestResetCounts`).
5. Scopes: a project reset moves only that repository's project count, never the factory month or another repository's (Task 1, `TestProjectResetScope`; Task 2, `TestProjectMonthSpendFollowsReset`).
6. Who may press: no CSRF, a bearer token, a writer who is no factory writer, an approver of another project: each refused, and nothing written (Task 3, `TestCapResetAccess`).
