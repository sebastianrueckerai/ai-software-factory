# Gas Town and Beads

## 1. What it is

Gas Town is a Go command-line tool (`gt`) by Steve Yegge that runs many coding agents in parallel, each in its own git worktree and tmux session, coordinated by named roles (Mayor, Polecat, Witness, Deacon, Boot, Refinery, Crew). Beads (`bd`) is a separate, standalone Go project, a Dolt-backed, git-synchronised graph issue tracker that Gas Town uses as its task store but that also works on its own with any coding agent. Both are MIT licensed, both live under the `gastownhall` GitHub organisation (moved there from Yegge's personal account during 2026), and both are free to self-host with no paid tier in the open-source code itself.

The maker's claim, from the README, the architecture docs and Yegge's own "Welcome to Gas Town" essay, is that a Bors-style merge queue plus a "witness" AI supervisor let a small number of humans run a "town" of dozens of autonomous polecats against a shared backlog, largely without a human approving each change. What the code actually shows is narrower on two counts checked directly against source: the README states "polecats never push directly to main", but `gt sling --merge=direct` and the `done` command push straight from a polecat's own worktree to the default branch with no gate and no merge queue involvement, a real, tested, documented bypass, not a bug. And the merge queue's own gate step (`runBatchGates`) returns success with zero checks run whenever no test command is configured, which is the out-of-the-box default.

A commercial layer sits above the open-source core. Kilo, an agentic coding company founded in March 2025 by GitLab co-founder Sid Sijbrandij, partnered with Yegge to launch "Gas Town by Kilo" as the only cloud-hosted managed version, reaching general availability on 19 May 2026, billed through Kilo's own multi-model gateway. A different entity, Gas City Inc, is building a follow-on declarative SDK on the same Beads and Dolt foundation, and a maintainer reply on the gastown issue tracker in 2026 states that gastown itself "is in maintenance mode and staying focused on infrastructure and reliability fixes only", with new feature requests redirected to Gas City. Beads, by contrast, was pushed to today (2026-09-29) and remains the most actively released part of the whole ecosystem.

## 3. Architecture and stack

Both tools are single Go binaries with no queueing system, no container runtime and no cloud dependency by default, everything can run on one laptop. Gas Town's `go.mod` pins Go 1.26.2 and depends directly on `github.com/steveyegge/beads`, `spf13/cobra` for the CLI, and `charmbracelet/bubbletea` plus `lipgloss` for its terminal UI. Beads' own `go.mod` pins Go 1.26.5, uses `cobra` and `viper`, and depends directly on Dolt's own Go packages (`dolthub/dolt/go`, `dolthub/go-mysql-server`, `dolthub/vitess`) for its embedded storage mode, plus `anthropic-sdk-go` for one specific feature, LLM-based compaction.

Storage is Dolt, a version-controlled, MySQL-wire-compatible database, in one of two modes selected at build time by a CGO flag (`beads_cgo.go` versus `beads_nocgo.go`). Embedded mode (`bd init`, the default for standalone Beads) runs Dolt in-process under `.beads/embeddeddolt/`, single writer, and requires CGO, the non-CGO build path explicitly refuses to fall back to it. Server mode (`bd init --server`) connects to an external `dolt sql-server` for concurrent writers. Gas Town's own `docs/design/architecture.md` states that Gas Town itself only ever runs the server mode, one Dolt SQL Server process per town on port 3307, because concurrent polecats need concurrent writers, this single process is a stated single point of failure in the same document. Gas Town talks to Dolt only by shelling out to the `dolt` CLI (`internal/doltserver/doltserver.go`), and to Beads only by shelling out to the `bd` CLI (`internal/beads/exec.go`, comment: "bd is a trusted internal tool"), it does not use Beads as an in-process library beyond shared types.

Cross-machine sync uses `bd dolt push` and `bd dolt pull` against `refs/dolt/data`, a git ref separate from ordinary branches and tags, so Dolt piggybacks on the same git remote's object store rather than a bespoke transport. `.beads/issues.jsonl` is confirmed by code, not just by the README, to be export-only, `cmd/bd/export_auto.go` only ever writes it from the database, nothing reads it back in as a write path.

Gas Town's two-level Beads layout keeps town-wide beads at `~/gt/.beads/` (prefix `hq-`, cross-rig coordination and Mayor mail) separate from rig-level beads at `<rig>/mayor/rig/.beads/` (project-specific, implementation work). Worktrees for polecats, refinery and crew hold a `.beads/redirect` file pointing back to the canonical rig database, and a `routes.jsonl` maps ID prefixes to rig paths for cross-rig lookups.

Work assignment goes through `gt sling`, described in its own comment as "THE unified work dispatch command", which can spawn a polecat, hand work to an existing agent, or dispatch to a formula. Beads' atomic claim (`bd update <id> --claim`, `bd ready --claim --json`) is a single conditional SQL UPDATE guarded by an optimistic-concurrency column (`row_lock`, surfaced in Go as `Issue.RowVersion`), first claim wins, a repeat claim by the same holder is idempotent. A merge-slot bead (`bd merge-slot create/acquire/release`) serialises conflict-prone work such as pushes to one branch, and Refinery's own `acquireMainPushSlot` uses the same kind of Dolt-backed lock, but only when the target is the rig's default branch.

Hierarchical IDs are dotted (`bd-a3f8.1.2`), capped at three levels deep. Hash-based IDs avoid merge collisions across branches, deterministically derived from title, description and creation time, tried at progressively longer lengths (6 to 8 base36 characters) with a nonce on collision, so two agents on two branches can each mint an ID with no coordination and no clash once merged. Dependency edge types go well beyond blocks and relates-to, the code defines `parent-child`, `duplicates`, `supersedes`, `replies-to`, `waits-for`, `caused-by`, `validates`, `tracks` and more.

Compaction ("memory decay") is real but narrower than the README's phrasing suggests. It is LLM-based, using Claude Haiku by default, with a 30-day and a 90-day threshold, and it is invoked by a human or a scheduled `bd compact`, not automatic. A second tier of compaction is partially coded (eligibility checks exist) but the CLI itself refuses to run it: "Tier 2 compaction is not yet implemented". Formula expansion into molecules and wisps, by contrast, is confirmed to be pure deterministic string templating, no model call anywhere in that path, a useful distinction between the parts of the system that are AI-driven and the parts that are not.

Workflow templating uses TOML "formulas", compiled (`bd cook`) into a frozen protomolecule, then either poured into a persistent, checkpointed molecule for expensive or crash-sensitive work, or expanded as a lightweight, root-only "wisp" for everyday steps, a deliberate choice the docs justify as cutting database row growth from roughly 6,000 rows a day to about 400.

The Refinery merge queue is genuinely implemented, `internal/refinery/batch.go` builds a rebase stack, runs gates once, fast-forwards on a pass, retries once on a suspected flake, and bisects to isolate a culprit on a repeated failure, matching the Bors algorithm the docs describe. The gap is the default configuration: with no test command set, the gate step returns success having run nothing, and a convoy set to `merge_strategy=direct` skips Refinery, gates and the batch pipeline altogether, pushing straight from a polecat's worktree to the default branch. A git pre-push hook does block direct pushes to most branches, but its own allow-list includes the default branch itself, commented "crew workers push here directly", and it checks the branch name, not who or what is pushing.

Supervision is layered by design, not accidentally. A cheap, mechanical daemon (three-minute heartbeat) checks for GUPP violations, the "Gas Town Universal Propulsion Principle", if there is work on your hook you must run it, using a 30-minute timeout, but the daemon is only allowed to notify the rig's Witness by mail, never to kill or restart anything itself. The project's own design docs call this the "murder spree lesson", mechanical detection of stuck work is fragile, so only an AI agent (the Witness) is trusted to judge whether a polecat is truly stuck and to act (nudge, restart, remove the sandbox, or escalate). A separate Deacon process does force-kill genuinely unresponsive sessions, after three consecutive 30-second ping failures and a five-minute cooldown between kills. Escalation severities (CRITICAL, HIGH, MEDIUM) route Deacon to Mayor to, if unresolved, an Overseer, with a stale-escalation auto-bump after four hours, this routing is implemented, not just documented, though a "future" table of finer-grained escalation categories in the same design doc is explicitly marked not yet built.

There is no Kubernetes integration anywhere in the code, a grep across the whole tree turns up only a hypothetical example formula name and a mention of a third-party, ecosystem-only "gastown-operator" that the project explicitly disclaims as not part of its core. Gas Town is a local, tmux-based orchestration tool.

## 4. UX

Everything happens in a terminal, and no screenshots exist in either cloned repository, so this section is built from README and design-doc prose, not from images. `gt feed` gives one merged, live, `bubbletea`-based TUI feed across every running polecat, `gt dashboard` serves a local htmx web dashboard alongside it. Because each polecat is its own tmux session, a human can also attach directly to any single agent's terminal and watch, or type into, that one session, a more granular "watch" primitive than a log viewer.

Onboarding for Beads alone is three commands from the README: run the install script, `bd init` in a project, then `bd setup <agent>` to wire up agent-specific instructions. Gas Town's own quickstart was not read step by step with the same rigour, so its exact step count from zero to a first running polecat is not verified here.

Intervention on a stuck agent is reactive, not a gate. A "Problems" view classifies each polecat's health (GUPP violation, stalled, zombie, working, idle) and offers nudge (send a corrective message without restarting) or handoff (context refresh or restart). There is no approval workflow found anywhere in the docs read that requires a human to sign off before Refinery merges a batch, the closest thing is severity-based escalation when something is already going wrong, not a routine pre-merge gate.

Compared with our own baseline, which admits to no real-time streams of an agent's work and no diff view, Gas Town's tmux-per-agent plus a merged feed is a genuinely better answer to "what does a human see while an agent works", whether it also gives a good diff view is not verified, no screenshot or firsthand walkthrough confirmed it. Our console has an explicit approval workflow, a cost view and a kanban board, none of which Gas Town's UX has an equivalent of in what was read.

## 5. Security, identity, sandbox, policy, cost

Sandboxing is absent by default, and this is a documented design choice, not an oversight discovered by reading between the lines. `SECURITY.md` states plainly that workers share filesystem access and that agents execute shell commands as the running user. Claude Code and Codex are both launched with vendor permission-bypass flags (`--dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`) with no opt-out in the default path, a design doc dated March 2026 names this directly as the current-state problem it hopes to fix: "every polecat today runs directly on the host machine... with full access to the host filesystem, network, and credentials." A real, opt-in mutual-TLS proxy with per-agent certificates exists in code (`internal/proxy/`, over 4,500 lines) for containerised deployments, but the container backend it was designed against does not exist in the repository, and every item on that design's own acceptance checklist is unchecked. The optional Docker image wraps the whole HQ workspace in one container for convenience, the README itself calls the dashboard port that exposes "a trusted local-network surface", not a security boundary.

Identity is the operator's own. Every polecat runs as the human's OS user, GitHub API access is one shared `GITHUB_TOKEN` for the whole host, and git push and pull use whatever credential store the operator already configured, an SSH agent or a stored token, with no per-agent issuance or rotation outside the unfinished proxy path. This is the direct opposite of a task-scoped, short-lived credential.

Policy is written in prose and TOML, not enforced in code an agent cannot bypass. Role directives (Mayor, Witness and so on) are markdown templates the agent reads, formulas are TOML the agent's own tools expand. The one out-of-band enforcement point found, the proxy's certificate denylist, is opt-in and, per the design doc's own checklist, unverified end to end.

Cost has no hard control anywhere in the code. `gt costs` and `gt costs digest` report and summarise spend into a daily bead, useful for visibility, not for stopping anything. A `cost-tier` setting only changes which model a role uses (Opus, Sonnet, Haiku), and `scheduler.max_polecats` exists to avoid exhausting a model provider's rate limit, not to cap a bill, its own docs frame it that way. A separate `internal/quota` package rotates between configured Claude accounts when one hits a provider rate limit, again a throughput workaround, not a spend control. Community cost research (Ry Walker, cited in Sources) puts agent-subscription cost at 20 to 100 USD a month per agent account, on top of token spend, and recommends heavy users budget 100 to 300 USD or more a month, with Hacker News commentary describing the tool as capable of "burning through thousands of dollars" at high concurrency, all of that is usage data, not anything the tool itself enforces.

## 6. What we should take from it

Narrow, code-level items we could copy this month. The optimistic-concurrency claim column (a `row_lock` compared and swapped in a single UPDATE, surfaced as `RowVersion`) is a clean, minimal pattern for race-free work assignment if we ever have more than one process pulling from the same queue, smaller than building a distributed lock. The schema-version guard, refuse to open a database a newer binary already migrated, print the exact fix command, and offer one named, deliberate escape hatch, is worth copying wherever our own agents touch a versioned store, fail loud with the fix in the error text rather than a bare SQL error. Deterministic, progressively-lengthened content-hash IDs let independent branches mint collision-free identifiers with no coordination, useful if we ever want task creation to work offline or across forks. LLM-based compaction of old closed work, bounded by an explicit day threshold and kept restorable via a snapshot, answers our own stated weakness in cross-task memory directly enough to prototype narrowly.

Broader, product-shape items. The "murder spree lesson", never let a cheap mechanical detector take a destructive action, only let it notify a stronger, judgment-making supervisor, is not a new idea for us, it is close to our own stall and repeated-failure detectors calling a supervisor model, but seeing an independent team land on the identical split, with the identical justification, is a useful cross-check that the design is sound. Treating live per-agent terminal access, not a log tail, as the default way a human watches work is a genuinely different answer to a problem our own baseline admits is unsolved (no real-time stream of an agent's work), the product shape, attach to the thing itself, is worth taking even if tmux specifically is not.

## 7. Where our philosophy differs and what that costs or buys us

Identity is the sharpest difference. Gas Town gives every agent the operator's real OS identity and real push credentials, which costs them nothing to integrate, an agent just inherits whatever access the human already has, and buys them zero exposure limiting, a badly prompted or compromised polecat can push anywhere the human can, using the human's own name. Our task-scoped, short-lived credential model is more to build and issue, it is also the entire reason a wayward agent cannot become a wayward human.

Isolation is the second. Gas Town shares one filesystem and OS user across every concurrent polecat, by its own admission, and starts agents with permission checks turned off. That buys speed of onboarding, no sandbox to provision, and costs the "security without half measures" constraint outright, one agent can read or corrupt another's work, and there is no default-deny network boundary at all. Our gVisor-per-task sandbox exists specifically to close the gap Gas Town leaves open by design.

Policy is the third. Gas Town's rules are prompts and TOML files the agent itself reads and, in principle, can be argued out of, the one out-of-band mechanism (the proxy's certificate denylist) is optional and unfinished. Our principle is that a prompt cannot grant a capability, policy lives in gateway code and network rules the model never touches. Adopting Gas Town's approach would be cheaper and would break this principle by construction, not by accident.

Cost is the fourth. Gas Town has visibility and a rate-limit workaround, not a cap, and the community's own cost estimates show what that looks like in practice. Our hard per-task, per-day and per-project caps cost more engineering, they are also why an agent stuck in a loop costs us a bounded amount, not an unbounded one.

Substrate is the fifth. One Dolt SQL Server per town is a named single point of failure in Gas Town's own architecture document, and a whole town lives on one host. Our Kubernetes substrate exists to make any one task, pod or node disposable. Gas Town's simplicity, nothing to cluster, is a real advantage for a single operator, it is also the trade-off that makes a direct port of their substrate a poor fit for our own re-seedable, commodity-hardware design.

## 8. Red flags and slop assessment

This reads as a real, actively developed pair of projects with a genuine commercial partner, not an abandoned demo, and it also carries more red flags than most projects in this series, for reasons unrelated to whether the code compiles.

The README overstates at least one safety claim the code contradicts. It states polecats never push directly to main, `gt sling --merge=direct` and the `done` command do exactly that, a real, tested, help-documented feature, not a bug, but the absolute wording in the README is false as written. The merge queue's own default gate configuration runs zero checks when no test command is set, which is the out-of-the-box state, so "verified before merge" depends entirely on operator configuration that the README does not foreground.

A GitHub issue on the tracker (gastownhall/gastown#3649, opened 2026) alleges that bundled release formulas caused installations to spend a user's own LLM credits and push commits to the maintainer's own repository under the user's own GitHub account, with no disclosure and no opt-out, confirmed in the issue thread by the reporter's own source citations (`internal/templates/roles/mayor.md.tmpl`, the release formulas) and corroborated by at least one other user in the comments who separately noticed their Mayor trying to open issues against the gastown repo itself on v1.0.0. The maintainer's own reply redirects the broader product question to the separate Gas City project and states gastown is in maintenance mode, without squarely resolving the disclosure complaint itself. The underlying behaviour, code that points agents at the maintainer's own tracker by default, is confirmed, whether it was malicious or careless design is not something this report can settle.

Separately, an unofficial memecoin named $GAS, built on the Solana-based Bags launchpad, paid Yegge creator and trading-fee royalties that he publicly disclosed in his own Medium post and later publicly distanced himself from, the token had already run to a roughly 60 million USD peak valuation on the back of his association before collapsing about 98 percent to roughly 1.1 million USD within days of his public distancing (around 19 January 2026), per Whale Alert. A widely repeated "300k profit" figure traces only to an unverified social-media post amplifying press coverage, not to an audited or on-chain-verified number, and should not be read as established fact. This is a reputational matter concerning the project's creator, not its code, cited here because anyone evaluating Gas Town will find it within one search, and because Bill de hÓra's otherwise appreciative architectural review of Gas Town also raises a substantive design critique worth taking seriously on its own terms, that GUPP ("always make progress") risks papering over a silent wrong-tool-selection failure instead of surfacing it, alongside open questions about structured-query context management versus RAG.

Weighed against those flags, the maintenance signal is real. Beads was pushed today, carries 118 changelog entries against gastown's 28, both repositories are MIT licensed with no sign of a licence change or a hidden paid tier in the open-source code, both have well over a hundred contributors, and the Kilo partnership is a named, live commercial relationship with a real general-availability date, not an announcement with nothing behind it. The most recent, most concrete maintenance evidence is the project's own incident report, `docs/recovery/accidental-1-2-1-release.md`, describing an untested v1.2.0 and v1.2.1 published by accident on 11 August 2026 that silently migrated any local database that ran them, fixed by re-releasing the tested prior line under a higher version number, with a public, detailed, working recovery procedure. That is what a used, evolving project's mistakes look like, not what an unmaintained one looks like. gastown itself, though, is now explicitly in maintenance mode by a maintainer's own words, with new product direction moving to the separate, unfunded-as-far-as-verified Gas City project, a genuine, stated narrowing of scope worth weighing against the headline star counts.
