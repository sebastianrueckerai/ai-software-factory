# Paperclip

## 1. What it is

Paperclip is an open-source control plane for running a company of AI agents. It defines agents in a strict reporting tree with roles and titles, gives each agent a monthly budget, wakes agents on a scheduled or event-driven "heartbeat" rather than running them continuously, and routes all work through issues with a fixed status lifecycle (backlog, todo, in_progress, in_review, done, with a blocked branch). The README's own framing: "If OpenClaw is an employee, Paperclip is the company." It ships under the MIT licence, is developed in the open by a large contributor base, and has no paid tier, managed cloud offering or disclosed company behind it as of today.

The README explicitly lists what Paperclip is not: not a chatbot, not an agent framework, not a workflow builder, not a prompt manager, not a single-agent tool, and not a code review tool. It positions itself purely as the orchestration and governance layer sitting above agent runtimes such as Claude Code, Codex, Cursor, Gemini, Hermes and OpenClaw, which it calls in through a pluggable adapter interface.

What the README claims: agents are managed like employees, with hiring, budgets, org charts and audit trails, and the user is "the board of directors." What the code shows: this framing is backed by a genuinely rich Postgres schema (agents, issues, goals, budget policies, execution policy and state, execution workspaces), not just UI decoration. It also shows the opposite of a security-first design in the default execution path: local adapters run as unsandboxed host processes, and the project's own security advisories record a critical unauthenticated remote code execution vulnerability, CVE-2026-41679, CVSS 10.0, as recently as April 2026, fixed reactively.

## 3. Architecture and stack

Backend: Node.js 24.11+, Express 5, TypeScript, Postgres 17 (or an embedded PGlite for zero-config local dev) accessed through the Drizzle ORM. Frontend: React 19, Vite 6, React Router 7, Radix UI, Tailwind CSS 4, TanStack Query. Auth: Better Auth, sessions and API keys. Monorepo: pnpm 9 workspaces (server, ui, cli, and a packages directory holding adapters, adapter-utils, db, shared, skills-catalog, teams-catalog, mcp-server, plugins, paperclip-runner, paperclip-eval-kernel). Confirmed by reading docs/start/architecture.md and the top-level directory layout.

Task state lives entirely in Postgres, read via the schema files under packages/db/src/schema (agents.ts, issues.ts, goals.ts, budget_policies.ts, all read in full). There is no separate workflow engine. Scheduling, retries and state machines are hand-rolled in server/src/services/heartbeat.ts and the issues table's own status and version columns, not delegated to something like Temporal.

How it runs agents: a scheduler wakes an agent for a bounded heartbeat (docs/agents-runtime.md), which dispatches to one of several built-in adapters, claude_local, codex_local, cursor, opencode_local, gemini_local, hermes_local, hermes_gateway, openclaw_gateway, process, http, plus external plugin adapters, or a custom plugin adapter (docs/adapters/creating-an-adapter.md). The default execution target is the local host process. A pluggable execution-target abstraction supports a sandbox transport, Daytona, e2b, Cloudflare, Modal, Novita, self-hosted Kubernetes on the roadmap, but this is only mandatory for the low_trust_review containment preset (doc/LOW-TRUST-PRESETS.md), not the default.

How it talks to models: it does not talk to models directly. Each adapter shells out to, or calls the API of, its own underlying CLI or runtime, already configured and authenticated on the host. A design document dated 2026-04-06 (doc/plans/2026-04-06-smart-model-routing.md) proposes an adapter-local, opt-in "cheap preflight model then primary model" pattern, explicitly rejecting a shared server-side router, and citing a competitor's own routing heuristic as prior art it chose not to copy. As of this read it is a proposal, status "Proposed," not yet universally implemented.

Deployment shape: a single Node process. Interactive local setup runs through a CLI onboarding command, and a separate command spins up a fully ephemeral trial instance. A manual path (install dependencies, then run the dev server) is also documented. Two deployment modes (docs/deploy/deployment-modes.md): local_trusted, loopback, no auth, and authenticated, private or public, gated by a login system, with a board-claim migration flow to move from one to the other. No Helm chart, Kubernetes manifest or docker-compose file was found for a production multi-node deployment. The docker directory holds narrower images, agent-runtime, daytona-runner, hermes-gateway-smoke, quadlet, untrusted-review, not a full stack.

## 4. UX

Onboarding to a first result is short. The ephemeral trial command is a single command that produces a fully disposable instance, no persistent install, no external Postgres. The persistent path, a signed install script, then an onboarding command with an auto-accept flag, is two commands, after which onboarding creates a first company, a first agent and a privileged "onboarding first task." This is confirmed in code: the issues table carries a race-safe unique index limiting a company to at most one issue whose origin kind is "onboarding first task," and the surrounding code comment states this grants privileged behaviour, an agent-attributed greeting and description suppression. This is markedly faster than our own console, which our baseline document admits has no onboarding at all.

While an agent works, a user watches through the issue thread, agent status comments, a live run view, and a workspace diff view. Repository screenshots (files named for a live run menu, before and after, and a workspace diff) confirm both exist, though these are pull-request visual-regression artefacts committed for a design-token and Storybook baseline process (DESIGN.md), not a curated marketing gallery. The remaining screenshot files are similarly before-and-after test fixtures for specific pull requests, not product screenshots. A user intervenes through the execution-policy API: only the active stage participant can act, and a decision comment must land in the same request as the status change (docs/guides/execution-policy.md), or through the website FAQ's stated ability to pause, reassign, or terminate any agent at any time.

Interfaces: a web UI (React), a CLI for install, onboarding and trial instances, and an HTTP API. No IDE plugin or chat interface is part of the core product, consistent with the README's "not a chatbot" framing.

Where Paperclip is easier than our console: a designed, componentised UI with an explicit design-token and visual-regression process, a genuine diff view, and a one-command, zero-commitment trial. Where it is worse or simply absent: no verification or CI view of any kind, since verification is out of scope, and no equivalent of our per-task cost or alert views tied to a wider factory loop, since Paperclip's loop stops at the company boundary.

## 5. Security, identity, sandbox, policy, cost

Security posture. The default execution mode trusts the host machine, not the task. docs/agents-runtime.md states outright that local CLI adapters run unsandboxed on the host machine. This is not a theoretical weakness. GitHub's security advisories for this repository, checked 2026-09-29, list twelve published advisories, the great majority landing on a single day, 2026-04-16, which reads as a post-hoc security audit rather than security designed in from the start. The headline is CVE-2026-41679, advisory id GHSA-68qg-g8mg-6pr7, CVSS 10.0: an unauthenticated attacker could self-register, approve their own CLI challenge, and import a new "company" containing a malicious process-adapter agent, whose configured command then executed as the Paperclip server, in a chain reported as six API calls. A widely used penetration-testing framework shipped an automated module for it in June 2026. Alongside it: CVE-2026-41208, advisory id GHSA-265w-rf2w-cjh4, CVSS 8.8, privilege escalation via an agent-controlled workspace provisioning command executed unchecked during workspace setup; a critical OS command injection via a workspace cleanup command passed verbatim to a shell spawn, advisory id GHSA-vr7g-88fq-vhq3; two separate cross-tenant compromises via missing company-scoping checks on agent API key routes, advisory ids GHSA-47wq-cj9q-wpmp and GHSA-3xx2-mqjm-hg9x, both CVSS 9.9; a drive-by remote code execution via DNS rebinding against local instances, advisory id GHSA-x8hx-rhr2-9rf7, CVSS 9.6, published 2026-07-22, with no patched version listed in the advisory data as of today; and a report that a codex adapter inherited an already-connected Gmail grant from the host's separate ChatGPT app and sent real outbound email, advisory id GHSA-gqqj-85qm-8qhf, CVSS 8.7, worsened by that adapter defaulting a "bypass approvals and sandbox" flag to true. All of this was read directly from the advisories, not from a secondary source.

Identity. In default local mode there is no per-task credential brokering. The environment-building function in packages/adapter-utils/src/server-utils.ts injects only an agent id, a company id and an API URL into the adapter's environment, nothing provider-specific. The stated assumption is that the CLI is already installed and authenticated on the host machine, which in practice means a long-lived, operator-scoped credential the agent process can reach. The opt-in sandbox path is a real exception: doc/architecture/paperclip-runner-daytona-networking.md describes a mediation process, one-use launch tickets, and an explicit claim that the model provider never receives a Paperclip or sandbox-vendor credential. That path is required only for the low_trust_review containment preset, not the default.

Sandbox. Not the default. doc/LOW-TRUST-PRESETS.md defines a standard versus low_trust_review containment split. Only the latter mandates the sandbox driver, an isolated workspace mode, and rejection of inline secrets. Everything else runs as an ordinary host process.

Policy. Two different pictures coexist in the same codebase. doc/MCP-ACCESS-GOVERNANCE.md describes a genuinely deny-by-default gateway for external tool connections, with resource-filter profiles, an approval flow for broad providers, and a call-event audit log, all enforced in code, not prompts. But the advisories above show the adapter and process execution path, which is the main way Paperclip actually does work, had no equivalent enforcement: agent-controlled configuration fields reached shell execution and file reads with no validation, and API routes were missing tenant-scoping checks. The connections threat model document (doc/connections/SECURITY-THREAT-MODEL.md) is honest about part of this in its own residual-risks section, stating that plugin workers are trusted runtime code today, not a hard sandbox.

Cost. The budget-policies table defines a generic scope, company or agent, plus window plus metric policy: a billed-cents metric by default, a configurable warn percentage, default 80, and a hard-stop-plus-auto-pause flag, default on. This is enforced by aggregating cost events recorded per heartbeat, that is, reactively, after spend has already happened, not by a pre-flight reservation. Combined with the fact that a local heartbeat has no timeout by default, a zero value means no timeout locally, a single run's worst-case spend before the next check catches it is, by design, unbounded. This is weaker than a hold-before-spend model.

## 6. What we should take from it

Narrow, copyable this month.

The execution-policy, execution-stage, stage-participant shape and its decisions audit table (docs/guides/execution-policy.md) generalise "who must approve, in what order, and what happened" far better than our single fixed approval gate. It would let a project define, say, a two-stage review, a peer review then a human, without new workflow code each time, and the access-control detail, that only the active participant may act, and the decision comment must arrive in the same request as the status transition, is a clean, small rule worth copying outright.

The budget-policies schema, one table, scope type, scope id, metric, window, amount, warn percent, hard-stop flag, is a clean generic shape worth copying outright. Our own budget model, per task, per day, per project envelope, could collapse onto the same shape without losing anything, and it would make a future per-role or per-repository budget a configuration row, not a schema change. Worth noting: Paperclip itself has not fully moved onto this shape. The agents table still carries its own budgetMonthlyCents and spentMonthlyCents columns side by side with the newer scoped budget-policies table, so we should copy the destination shape, not the migration path.

The task-watchdog pattern (doc/TASK-WATCHDOG.md) is a distinct idea from our stall-detecting supervisor. It fires only once an entire issue subtree has come to rest, and asks a second agent to judge whether the stop was legitimate, not whether the run is stuck. This is a good complement to our gate-supervision timers, which only catch runs that are still going, not runs that quietly, wrongly, declared victory.

The ephemeral trial instance command, one command, a fully disposable instance, is worth copying as a pattern for our own console: a zero-state, zero-commitment way to see the factory work before anyone provisions real infrastructure.

Broad, product-shape level.

Treating a review stage as a per-issue-configurable object rather than a single approve-or-auto branch is a genuine product idea, not just a schema trick. It means the same control plane can express no review, one human, two agents then a human, or a low-trust preset with a mandatory sandbox plus human, as data, not as new code paths. Landing this in our design would mean generalising our current binary approval gate into a small state machine, which is a bounded, worthwhile piece of work.

The org-chart and role framing, a reporting-line tree, titles, delegation, is a UX device aimed at humans supervising many agents at once. We only run one capability class today, so it is not urgent, but if we ever add analyzer, integration-tester or release-agent classes as planned, a visual chain of responsibility would address our own console's admitted weaknesses, no onboarding, no real-time view, faster than building each view from nothing.

## 7. Where our philosophy differs and what that costs or buys us

Paperclip trusts the host by default, we mean to trust the task. Its default adapters run as ordinary host processes with only an agent id, a company id and an API URL injected, relying on a CLI already authenticated on that machine, an operator-scoped, long-lived credential reachable from agent-controlled code. Our design gives each task its own short-lived, narrowly scoped identity, so a compromised task cannot reach past its own grant. The twelve published advisories, several of them agent-controlled configuration fields reaching a shell or a file path unchecked, are close to the exact failure this principle exists to prevent. The cost of our approach is more moving parts, a credential broker, short-lived tokens, per-task scoping, where Paperclip's approach ships faster and runs anywhere a developer already has a CLI logged in.

Paperclip's scope is the whole AI company, hiring, goals, delegation, day to day work, with review as one configurable stage among several, not a mandatory separate plane. Our design keeps verification, tests, security, stronger-model review, policy evaluation, as a non-optional plane between worker output and merge. The company framing is broader and more ambitious as a product story. Our narrower framing buys a guarantee Paperclip does not make: nothing merges without passing through the same gate, however its execution policy is configured for that issue. That guarantee is worth more to us than the extra breadth would be.

Paperclip's policy enforcement is real but split unevenly across the system. The MCP Access Governance gateway is a solid deny-by-default control for external tool connections, with an audit log and an approval flow enforced in code. But the same rigor did not extend to the adapter and process execution path until an external audit apparently forced it, in April 2026, well after the project had accumulated tens of thousands of stars and forks. Our aim is a single enforcement point all task execution routes through, so a gap in one adapter cannot become a company-wide compromise. Paperclip shows what happens when policy is strong in one place and thin in the place doing most of the actual work: the thin place is where the CVSS 10.0 finding was.

## 8. Red flags and slop assessment

Not slop. This is a real, heavily used, actively developed project, not a demo repository. As of 2026-09-29, gh api reports 93,920 stargazers, 15,980 forks and 6,038 open issues, created 2026-03-02 and pushed as recently as this morning. The documentation set runs to dozens of files covering execution policy, budgets, watchdogs, MCP governance, low-trust presets and a Daytona sandbox architecture, in more depth than a typical hobby project bothers with. CONTRIBUTING.md requires a deduplication search before filing, a structured PR template naming which model produced the change, and a minimum automated review score before merge. This is what a project run in anger looks like, not a portfolio piece.

The security history is the strongest counterweight. Twelve published advisories, most landing in a single day, headlined by an unauthenticated CVSS 10.0 remote-code-execution chain reachable in six API calls, two separate CVSS 9.9 cross-tenant compromises, and a CVSS 9.6 drive-by RCE via DNS rebinding still without a listed patched version as of today, is a serious pattern for a project handling agent credentials and arbitrary code execution by design. It does not by itself mean the project is abandoned or fake. It does mean early growth outran security review, and that the safe-by-default posture we want is not what a new self-hosted deployment gets out of the box.

The company and funding picture is murky and not verified here. Search results describe a fast-growing, well-known pseudonymous maintainer and third-party commentary on growth and monetisation plans, but nothing in the repository or the fetched website states a funding round, a company entity or a monetisation plan directly. Treat all commentary on funding, headcount or company status as unverified secondary source material, not fact.

Net: genuine, actively maintained, widely adopted, with a real and serious security track record that anyone self-hosting it today needs to read in full before turning on anything beyond the default local, unauthenticated, single-user setup.
